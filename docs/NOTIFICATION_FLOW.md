# Notification Flow

This document describes the runtime path of a notification request from HTTP ingress to final delivery outcome.

## Overview

The flow has two phases:
- Intake phase: accept event and create delivery jobs
- Execution phase: poll jobs and deliver through provider adapters

## Step-by-Step Flow

### 1. HTTP request received
`POST /notifications/send` is handled by the notifications HTTP adapter.
The adapter validates schema and creates `SendNotificationCommand`.

### 2. Routed to `SendNotificationUseCase`
The route invokes `SendNotificationUseCase.execute(command)`.
This is the application entry point for notification intake.

### 3. Idempotency check
The use case builds an event fingerprint, then a per-channel fingerprint.
For each channel candidate, it performs an atomic `claim(dedupe_key)`.
If claim fails, that channel job is treated as duplicate and skipped.

### 4. Rate limiting check
Before heavy orchestration, `RateLimitService.allow_workspace(workspace_id)` is evaluated.
If denied, the request returns without creating jobs.

### 5. Channel selection
The channel repository returns active channels for the workspace.
This enforces workspace-scoped routing boundaries.

### 6. DeliveryJob creation
For each eligible channel:
- Message is generated by event message mapper
- Delivery job entity is created with `PENDING` status
- Retry and lifecycle metadata are initialized

### 7. Job enqueued (persisted queue)
The delivery job is stored through `DeliveryJobRepositoryPort.save(job)`.
In current runtime, this is an in-memory persistence adapter acting as a queue store.

### 8. Worker polls jobs
`NotificationWorker` runs continuously.
It polls due jobs using `get_pending_jobs(limit=50)` with a sleep interval between loops.

### 9. `ProcessDeliveryJobUseCase` executes
For each polled job:
- Status transitions to `PROCESSING`
- Updated state is persisted
- Provider sender is resolved through sender registry

### 10. Provider sends message
The resolved outbound adapter (for example Telegram) executes `send(job)`.
Provider adapter is responsible only for delivery API interaction.

### 11. Success / retry / failure handling
If send succeeds:
- Job status becomes `SUCCESS`

If send fails transiently and retry budget remains:
- `retry_count` increments
- `next_retry_at` is scheduled using exponential backoff
- Status moves back to `PENDING`

If failure is permanent or retries are exhausted:
- Status becomes `FAILED`
- `last_error` is recorded

## Resulting Guarantees

- Workspace-level rate admission control
- Race-safe dedupe for intake
- Persisted lifecycle transitions
- Bounded retries with backoff
- Clear terminal state (`SUCCESS` or `FAILED`)
